================================================================================
  1. PROJECT OVERVIEW
================================================================================

VacanSee is a full-stack web application for browsing and booking boarding
houses in the Philippines. It has two roles:

  TENANT (regular user)
    - Browse/search listings
    - View property details
    - Submit booking requests
    - Send messages to admin
    - Save/favorite properties
    - Write reviews
    - Track their own bookings

  ADMIN (admin@vacansee.com)
    - Manage property listings (Add / Edit / Delete)
    - Approve or reject booking requests
    - Reply to tenant messages/inquiries
    - See all activity in one dashboard


================================================================================
  2. TECH STACK & WHY EACH WAS CHOSEN
================================================================================

FRONTEND
  React 19         - Component-based UI library. Each page/widget is a
                     self-contained component with its own state. Re-renders
                     only what changed (not the whole page).

  React Router 7   - Client-side routing. Lets us navigate between /browse,
                     /dashboard, /listing/:id etc. without a full page reload.
                     This is what makes it an SPA (Single Page Application).

  Create React App - Zero-config build tool. Handles bundling, transpiling
                     JSX, and running the dev server with "npm start".

  CSS (plain)      - 14 modular CSS files imported into App.css. Variables
                     defined in variables.css for easy theming. Dark mode via
                     the data-theme="dark" attribute on <html>.

BACKEND
  Spring Boot 3.2  - Java framework that creates a REST API server. Handles
                     HTTP requests, talks to the database, and sends back JSON.

  Spring Security  - Handles password encoding (BCrypt). All API routes are
                     set to permitAll() because session auth is handled by
                     localStorage on the frontend, not server-side tokens.

  Spring Data JPA  - Makes database queries easy. Instead of writing raw SQL,
                     you write method names like findByUserId(Long userId) and
                     JPA generates the SQL automatically.

  Hibernate        - ORM (Object-Relational Mapper). Maps Java classes (models)
                     to MySQL database tables. ddl-auto=update means it creates
                     or alters tables automatically on startup without losing data.

  MySQL 8          - Relational database. Stores all persistent data: users,
                     properties, bookings, inquiries, reviews, favorites.

  Lombok           - Library that auto-generates Java boilerplate. @Data adds
                     getters, setters, equals, hashCode. @NoArgsConstructor and
                     @AllArgsConstructor add constructors. Saves hundreds of
                     lines of repetitive code.

================================================================================
  4. HOW THE APP STARTS (BOOT SEQUENCE)
================================================================================

BACKEND STARTUP (Spring Boot)
──────────────────────────────
  1. VacanSeeApplication.java runs. @SpringBootApplication tells Spring to scan
     all classes in the package and wire them together.

  2. application.properties is read:
       - Server starts on port 8000
       - Connects to MySQL at localhost:3306/appdevdb
       - If "appdevdb" does not exist, MySQL creates it automatically
         (createDatabaseIfNotExist=true in the connection URL)

  3. Hibernate reads all @Entity classes (User, Property, Booking, etc.) and
     creates or updates the corresponding MySQL tables (ddl-auto=update).

  4. DataInitializationConfig.java runs:
       - Checks if admin@vacansee.com exists → creates it if not
         (password "admin123" is BCrypt-hashed before storing)
       - Checks if any properties exist → seeds 6 sample properties if not

  5. All @RestController classes register their URL mappings.
     The server is now listening on http://localhost:8000

FRONTEND STARTUP (React)
─────────────────────────
  1. index.js is the entry point. It renders <App /> into the <div id="root">
     in public/index.html.

  2. App.jsx mounts:
       - Reads localStorage to restore login state (userId, userRole, isLoggedIn)
       - Calls loadPropertiesFromBackend() to fetch and cache all properties
       - Sets up all routes using React Router

  3. The browser shows the Home page (/) by default.


================================================================================
  5. CORE DATA FLOWS (step-by-step)
================================================================================

─────────────────────────────────────────────────────────────
5A. AUTHENTICATION — REGISTER & LOGIN
─────────────────────────────────────────────────────────────

REGISTER:
  [User fills form on /register]
        │
        ▼
  Register.jsx → authService.register({ fullName, email, password })
        │
        ▼
  authService.js: POST http://localhost:8000/api/auth/register
  Body: { "fullName": "...", "email": "...", "password": "...", "phone": "" }
        │
        ▼
  AuthController.java:
    1. Checks if email already exists in users table
    2. If duplicate → returns 409 Conflict { message: "Email already registered" }
    3. If new → BCryptPasswordEncoder encodes the password
    4. Saves new User to MySQL
    5. Returns { userId, email, fullName, message: "User registered successfully" }
        │
        ▼
  Register.jsx receives response:
    - Stores userId, userEmail, userFullName, userRole="user", isLoggedIn="true"
      in localStorage (browser storage, persists on refresh)
    - Shows success message → redirects to /dashboard after 1.5 seconds

LOGIN:
  [User fills form on /login]
        │
        ▼
  Login.jsx → authService.login(email, password)
        │
        ▼
  authService.js: POST http://localhost:8000/api/auth/login
  Body: { "email": "...", "password": "..." }
        │
        ▼
  AuthController.java:
    1. Finds user by email in MySQL (userRepository.findByEmail)
    2. BCryptPasswordEncoder.matches(inputPassword, hashedPassword)
    3. If mismatch → 401 Unauthorized { message: "Invalid email or password" }
    4. If match → returns { userId, email, fullName, message: "Login successful" }
        │
        ▼
  Login.jsx:
    - Stores same localStorage keys
    - Checks if email === "admin@vacansee.com"
      → If admin: sets userRole="admin", navigates to /admin
      → If user:  sets userRole="user", navigates to /dashboard

WHY localStorage?
  We don't use JWT tokens for requests because Spring Security is set to
  permitAll() — every endpoint accepts anyone. The localStorage values
  are only used by the React frontend to decide what UI to show (protected
  routes, admin vs tenant views). This is acceptable for a school project;
  a production app would send the JWT as a Bearer token in request headers.

─────────────────────────────────────────────────────────────
5B. BROWSING & SEARCHING PROPERTIES
─────────────────────────────────────────────────────────────

  [App.jsx mounts] ──→ loadPropertiesFromBackend() ──→
        │
        ▼
  appData.js: GET http://localhost:8000/api/properties?page=0&size=500
        │
        ▼
  PropertyController.java:
    - Queries all properties using Hibernate pagination (PageRequest.of(0, 500))
    - Returns: { content: [ {id, title, price, city, ...}, ... ], totalElements, totalPages }
        │
        ▼
  appData.js normalize():
    - Converts BigDecimal price strings to JavaScript numbers (Number(p.price))
    - Stores the array in localStorage["vs_properties"]

  [User navigates to /browse]
        │
        ▼
  Browse.jsx:
    1. useEffect calls loadPropertiesFromBackend() again (fresh fetch)
    2. Then calls getAllListings() which reads from localStorage["vs_properties"]
    3. If backend offline → getAllListings() falls back to MOCK_LISTINGS (hardcoded)
    4. User applies filters → JavaScript .filter() and .sort() on the array
       (no extra server calls — all filtering is done in-browser)
    5. Results displayed as <Card> components

FILTERS AVAILABLE ON BROWSE:
  - Search text: matches title, city, or state (case-insensitive)
  - Property type: exact match on propertyType field
  - Min/Max price: filters by price range
  - Bedrooms: "2+ bedrooms" means bedrooms >= 2
  - Amenity: checks boolean flags (hasWifi, hasMeals, hasParking, etc.)
  - Sort: .sort() by price ascending or descending

─────────────────────────────────────────────────────────────
5C. BOOKING A PROPERTY
─────────────────────────────────────────────────────────────

  [User views /listing/:id]
        │
        ▼
  ListingDetails.jsx:
    - useParams() extracts the ID from the URL
    - getListingById(id) finds the property in localStorage cache
    - Displays details, amenities, reviews

  [User picks move-in date, number of months, clicks "Confirm Booking"]
        │
        ▼
  ListingDetails.jsx → adminData.addBooking({...})
        │
        ▼
  adminData.js: POST http://localhost:8000/api/bookings
  Body: {
    "property": { "id": 1 },
    "user": { "id": 5 },
    "checkInDate": "2025-07-01",
    "checkOutDate": "2025-08-01",  ← calculated: checkIn + (months × 30 days)
    "numberOfGuests": 1,
    "totalPrice": 3500,
    "status": "pending",
    "notes": "Booking for 1 month(s)"
  }
        │
        ▼
  BookingController.java:
    1. Validates property and user both exist in MySQL
    2. Sets status = "pending"
    3. Saves Booking to MySQL
    4. Returns BookingDTO (flat object without circular references)
        │
        ▼
  adminData.js:
    - Normalizes the BookingDTO with normBooking()
    - Appends to localStorage["vs_bookings"] cache

  [Step advances to "Message the Owner" screen]
    - User can optionally type a message → flows through 5D below
    - Or clicks "Skip" → redirected to /dashboard

─────────────────────────────────────────────────────────────
5D. SENDING A MESSAGE / INQUIRY
─────────────────────────────────────────────────────────────

  [After booking, user types a message and clicks "Send Message"]
        │
        ▼
  ListingDetails.jsx → adminData.addMessage({...})
        │
        ▼
  adminData.js: POST http://localhost:8000/api/inquiries
  Body: {
    "property": { "id": 1 },
    "inquirer": { "id": 5 },
    "subject": "Inquiry about Cozy Boarding House near UP Diliman",
    "message": "Hi! I would like to ask about...",
    "email": "user@email.com",
    "phone": ""
  }
        │
        ▼
  InquiryController.java:
    1. Finds property and user in MySQL
    2. Sets status = "pending", isRead = false
    3. Saves Inquiry to MySQL
    4. Returns the saved Inquiry object
        │
        ▼
  adminData.js:
    - Normalizes response with normInquiry()
    - Appends to localStorage["vs_messages"] cache

  WHERE THE USER SEES IT:
    /messages page → Messages.jsx fetches GET /api/inquiries/user/{userId}
    ChatBox widget → reads localStorage["vs_messages"] directly (sync)

─────────────────────────────────────────────────────────────
5E. ADMIN: MANAGING LISTINGS (Add / Edit / Delete)
─────────────────────────────────────────────────────────────

  [Admin opens /admin → Listings tab]
        │
        ▼
  AdminDashboard.jsx → loadAll() →
    getAdminListings() → GET /api/properties?page=0&size=200

  ADD LISTING:
  [Admin fills form, clicks "Add Listing"]
        │
        ▼
  adminData.addListing(formData):
    - Reads ownerId from localStorage["userId"] (admin's database ID)
    - POST /api/properties
    Body: { title, description, price, city, bedrooms, ..., ownerId }
        │
        ▼
  PropertyController.java:
    1. Finds the owner (admin) in MySQL by ownerId
    2. Creates Property entity, links to owner
    3. Saves to MySQL → returns PropertyDTO
        │
        ▼
  adminData.js:
    - Appends to localStorage["vs_admin_listings"] and localStorage["vs_properties"]
    - The listing immediately appears in Browse/Search without page refresh

  EDIT LISTING:
    - PUT /api/properties/{id} with updated fields
    - PropertyController updates only non-null fields (null-safe patch pattern)

  DELETE LISTING:
    - DELETE /api/properties/{id}
    - PropertyController FIRST deletes all related records:
        1. PropertyImages linked to this property
        2. PropertyFavorites (saves/hearts) for this property
        3. Inquiries about this property
        4. Bookings for this property
        5. Reviews for this property
    - Then deletes the property itself
    - This order is required because MySQL enforces foreign key constraints:
      you cannot delete a parent row if child rows still reference it.

5G. ADMIN: REPLYING TO MESSAGES
─────────────────────────────────────────────────────────────

  [Admin clicks Reply on a message, types reply, clicks "Send Reply"]
        │
        ▼

5H. CANCEL A BOOKING (USER SIDE)
─────────────────────────────────────────────────────────────

  [User sees pending booking on Dashboard, clicks "Cancel"]
        │
        ▼
  Dashboard.jsx → window.confirm() → if confirmed →
  adminData.cancelBooking(id)
        │
        ▼

        │ (same endpoint as admin approve/reject, just different status value)

5I. WRITING A REVIEW
─────────────────────────────────────────────────────────────

  [User is on /listing/:id, scrolls to Reviews section, writes review]
        │
        ▼
  ListingDetails.jsx → handleSubmitReview() →
    POST http://localhost:8000/api/reviews
    Body: { "propertyId": 1, "userId": 5, "rating": 4, "comment": "Great place!" }
        │
        ▼
  ReviewController.java:
    1. Validates rating is 1–5
    2. Finds property and user
    3. Saves PropertyReview to MySQL
    4. Returns ReviewDTO (with userName, not password)

─────────────────────────────────────────────────────────────
5J. SAVING / UNSAVING A PROPERTY (Heart Button)
─────────────────────────────────────────────────────────────

  [User clicks the heart icon on a Card or on ListingDetails]
        │
        ▼
  adminData.toggleSaved(propertyId):
    - Reads localStorage["savedListings"] array
    - If ID is in array → removes it (unsave)
    - If ID not in array → adds it (save)
    - Writes updated array back to localStorage
    - Returns the updated array

  NOTE: Saved listings are stored ONLY in localStorage, not in MySQL.
  This means saves are per-device/per-browser. The FavoriteController
  and PropertyFavorite model exist in the backend but are not yet
  connected to this frontend flow — the backend is ready for it but the
  frontend currently uses the simpler localStorage approach.


================================================================================
  6. FRONTEND FILE-BY-FILE PURPOSE
================================================================================

App.jsx
  The root of the entire React app. Defines all URL routes using React Router.
  Wraps everything in <Router> so navigation works. Passes isLoggedIn state
  to Navbar and protected pages. Restores login state on page refresh by
  reading localStorage in useEffect.

  Key routing logic:
    /dashboard → only accessible if isLoggedIn AND NOT admin
    /admin     → only accessible if isAdmin
    /messages  → only accessible if isLoggedIn
    If not logged in → <Navigate to="/login" /> redirects automatically

index.js
  The very first file that runs. Finds <div id="root"> in public/index.html
  and renders the entire React app into it. Wraps in <React.StrictMode> to
  catch common mistakes during development.

─── PAGES ───────────────────────────────────────────────────

Home.jsx
  Landing page. Shows Hero banner with search, stats section, featured listings
  (up to 6, filtered by amenity tabs), amenities strip, how-it-works steps,
  and a CTA (call-to-action) section. Calls loadPropertiesFromBackend() on
  mount to get fresh data.

Browse.jsx
  Full property listing page with a sidebar of filters. All filtering is done
  in JavaScript (client-side) — no extra API calls per filter change. Shows
  result count and supports grid/list view toggle.

Search.jsx
  Similar to Browse but reads initial values from URL search params
  (?location=Cebu&maxPrice=5000). This is how the SearchBar in the Hero
  passes its values to this page.

ListingDetails.jsx
  Displays a single property by ID. Has a 3-step right panel:
    Step 1 (FORM): User picks move-in date and months, sees total price
    Step 2 (MESSAGE): After booking, asks user to optionally message owner
    Step 3 (DONE): Shows success animation before redirecting
  Also shows amenities, property info, and the reviews section.

Login.jsx
  Simple form. Calls authService.login(). Has a collapsible demo credentials
  hint (hidden by default). On success: stores session to localStorage,
  navigates to /dashboard or /admin based on email.

Register.jsx
  Simple form with validation. Password must be ≥6 characters and match
  confirmPassword. On success: shows inline message, auto-redirects to
  /dashboard after 1.5 seconds.

Dashboard.jsx
  Tenant's home screen after login. Shows 4 stat boxes (bookings, pending,
  confirmed, saved count), a list of booking requests with status pills,
  a cancel button for pending bookings, and up to 3 saved properties.

Profile.jsx
  Allows user to edit their display name (saved to localStorage only —
  no PATCH /api/users endpoint exists yet). Shows booking stats pulled
  async from the backend. Has notification preference toggles (UI only,
  not saved to backend).

  SecurityConfig to ensure OPTIONS preflight requests also pass through.

  @Configuration class that implements CommandLineRunner via a @Bean method.
  This runs ONCE when the server starts. It:
    1. Creates the admin account if it doesn't exist (idempotent — safe to run
       multiple times without creating duplicates)
    2. Seeds 6 sample properties if the properties table is empty
  Purpose: ensures the app has working data out of the box without manual SQL.

WebConfig.java
  Configures static resource serving. Since the React build can be placed in
  the Spring Boot static/ folder, Spring Boot can serve both the API and the
  built frontend from port 8000.

─── DTOs (Data Transfer Objects) ────────────────────────────

DTOs exist to prevent two problems:
  1. Circular references — if Booking holds a Property which holds a User
     which holds Bookings, Jackson (JSON serializer) would loop forever.
     DTOs flatten this into a safe, simple object.
  2. Sensitive data leakage — the User model has a password field. DTOs
     only expose the fields that the frontend actually needs.

BookingDTO: id, propertyId, propertyTitle, propertyPrice, propertyCity,
            userId, userName, userEmail, checkInDate, checkOutDate,
            numberOfGuests, totalPrice, status, notes, createdAt

PropertyDTO: all property fields + ownerId (not the full owner object)

ReviewDTO: id, propertyId, propertyTitle, userId, userName, rating,
           comment, createdAt

AuthResponseDTO: userId, email, fullName, message
UserDTO: id, email, fullName, phone, bio, profileImage (NO password)

─── REPOSITORIES ────────────────────────────────────────────

Each repository extends JpaRepository<EntityType, IDType>.
JpaRepository provides: findAll(), findById(), save(), deleteById(),
count(), existsById() — all for free.

Custom query methods use Spring Data's derived query naming convention:
  findByUserId(Long userId)
  → Spring generates: SELECT * FROM bookings WHERE user_id = ?

  findByPropertyId(Long propertyId)
  → SELECT * FROM inquiries WHERE property_id = ?

  findByUserIdAndPropertyId(Long userId, Long propertyId)
  → SELECT * FROM property_favorites WHERE user_id = ? AND property_id = ?

  existsByEmail(String email)
  → SELECT COUNT(*) FROM users WHERE email = ? > 0

No SQL needed — just the method name.

  8. DATABASE TABLES & RELATIONSHIPS
================================================================================

MySQL database name: appdevdb

TABLES:
  users               ← one row per account
  properties          ← one row per listed boarding house
  bookings            ← one row per booking request
  inquiries           ← one row per message sent by a tenant
  property_reviews    ← one row per review
  property_favorites  ← one row per saved/hearted property
  property_images     ← one row per uploaded image (future use)

RELATIONSHIPS:
  users ──< properties       (one user/owner can have many properties)
  users ──< bookings         (one user can make many bookings)
  users ──< inquiries        (one user can send many inquiries)
  users ──< property_reviews (one user can write many reviews)
  users ──< property_favorites

  properties ──< bookings         (one property can have many bookings)
  properties ──< inquiries        (one property can receive many inquiries)
  properties ──< property_reviews
  properties ──< property_favorites
  properties ──< property_images

This is a standard one-to-many relationship. In MySQL, the "many" side
stores the foreign key (e.g. bookings.property_id, bookings.user_id).

FOREIGN KEY IMPLICATION:
  You CANNOT delete a property if bookings still reference it. MySQL
  enforces this to prevent orphaned records (bookings with no property).
  This is why PropertyController.deleteProperty() deletes all dependent
  records BEFORE deleting the property itself.

ADMIN ACCOUNT:
  The admin is just a regular user in the users table with email
  "admin@vacansee.com". The React frontend detects admin role by checking
  if the logged-in email matches this address — there is no role column
  in the database.

================================================================================
  10. KEY PATTERNS & DESIGN DECISIONS
================================================================================

PATTERN 1: API-FIRST WITH LOCALSTORAGE FALLBACK
  Every data fetch tries the backend first. If the backend is offline or
  throws an error, it falls back to cached data in localStorage.
  Example in adminData.js:
    try {
      const data = await tryFetch(`${API}/bookings`);
      lsSet("vs_bookings", data);           // update cache
      return data;
    } catch {
      return lsGet("vs_bookings");          // use cached version
    }
  WHY: The app stays usable even when MySQL or Spring Boot is down.

PATTERN 2: DATA NORMALIZATION
  Backend returns price as BigDecimal (e.g. "3500.00" as a string in JSON).
  Frontend needs it as a JavaScript number for math and .toLocaleString().
  normalize() in appData.js converts it: Number(p.price) || 0
  normBooking() in adminData.js handles the same for booking data.
  WHY: Prevents "3500.00" + 1 = "3500.001" (string concatenation vs addition).

PATTERN 3: DTO PATTERN
  The backend never returns raw Entity objects in API responses. Instead it
  converts to DTO (Data Transfer Object) first.
  WHY TWO REASONS:
    1. Circular reference prevention: Booking → Property → Owner(User) →
       Bookings → (loop). Jackson would crash serializing this.
    2. Security: User entity has a password field. DTOs exclude it.

PATTERN 4: LOCALSTORAGE SESSION
  After login, the frontend stores: userId, userEmail, userFullName, userRole,
  isLoggedIn in localStorage.
  WHY localStorage instead of sessionStorage?
    localStorage persists after the browser tab is closed. This means users
    stay logged in when they refresh the page or close and reopen the tab.

PATTERN 5: ROLE DETECTION BY EMAIL
  Admin role is determined by checking if email === "admin@vacansee.com".
  There is no role column in the database; no JWT role claims; no server-side
  session. The check happens in Login.jsx when storing userRole to localStorage.
  WHY: Simpler implementation. Acceptable for a school project.
  Production concern: a user could manually set localStorage["userRole"]="admin"
  in the browser console. In production, role should be server-enforced.

PATTERN 6: DERIVED QUERY METHODS (Spring Data JPA)
  Repositories declare methods like:
    List<Booking> findByUserId(Long userId);
  Spring Data reads the method name and automatically generates SQL:
    SELECT * FROM bookings WHERE user_id = ?
  This means ZERO SQL code written anywhere in the backend for simple queries.

PATTERN 7: CASCADE DELETE (Manual)
  Java/Hibernate can do automatic cascade deletes if the parent entity
  declares the relationship and uses CascadeType.ALL or orphanRemoval=true.
  We chose NOT to do this and instead manually delete in PropertyController:
    imageRepository.deleteAll(...);
    favoriteRepository.deleteAll(...);
    inquiryRepository.deleteAll(...);
    bookingRepository.deleteAll(...);
    reviewRepository.deleteAll(...);
    propertyRepository.deleteById(id);
  WHY: Explicit is clearer for a school project. CascadeType.ALL requires
  adding bidirectional @OneToMany fields to the Property entity, which also
  increases the risk of circular references in JSON serialization.

PATTERN 8: @JsonIgnoreProperties
  Every @ManyToOne relationship in the models has this annotation:
    @JsonIgnoreProperties({"password", "bookings", "inquiries", ...})
  WHY: When Jackson serializes a Booking, it also serializes the embedded
  User object. Without @JsonIgnoreProperties, it would try to serialize
  User.bookings which contains more Booking objects, causing infinite recursion.
  This annotation tells Jackson: "stop here, don't follow these fields."

PATTERN 9: DDLAUTO=UPDATE
  application.properties has: spring.jpa.hibernate.ddl-auto=update
  WHY: Hibernate automatically creates tables that don't exist and alters
  tables if the Entity class changes (adds columns). It NEVER drops tables.
  This means you don't need to write CREATE TABLE SQL manually.
  Danger in production: you can accidentally cause data loss with schema
  changes. Production apps use "validate" or managed migrations (Flyway/Liquibase).

PATTERN 10: BCRYPT PASSWORD HASHING
  Passwords are NEVER stored as plain text. BCryptPasswordEncoder.encode()
  creates a one-way hash like:
    $2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lihS
  BCrypt automatically includes a random salt, so the same password produces
  a different hash each time.
  BCryptPasswordEncoder.matches(rawPassword, storedHash) returns true/false.
  WHY: If the database is ever breached, attackers cannot recover passwords.


================================================================================
  11. COMMON PROFESSOR QUESTIONS & ANSWERS
================================================================================

Q: Why did you choose React for the frontend?
A: React uses a component-based architecture, which means each UI piece
   (Card, Navbar, ChatBox) is a self-contained, reusable module. It only
   re-renders what changed, not the full page, making the UI fast. React
   Router enables client-side navigation so the app feels like a native app.

Q: Why Spring Boot for the backend?
A: Spring Boot is a production-grade Java framework that removes boilerplate.
   It auto-configures the server, database connection, and security. Spring
   Data JPA eliminates SQL code for common queries. It follows REST principles
   which pairs naturally with a React frontend.

Q: What is REST? Is this a REST API?
A: REST (Representational State Transfer) is a design style for APIs using
   HTTP methods to represent actions: GET=read, POST=create, PUT=update,
   DELETE=delete. Our API follows this: POST /api/bookings creates a booking,
   DELETE /api/properties/1 deletes property 1. Responses are JSON.

Q: What is the difference between GET, POST, PUT, PATCH, DELETE?
A: GET    — Read data, no body, safe (no side effects)
   POST   — Create new resource, body contains the new data
   PUT    — Full update, replaces all fields of a resource
   PATCH  — Partial update, only changes specified fields
             (e.g. PATCH /bookings/1/status only changes the status field)
   DELETE — Remove a resource

Q: Why do you use localStorage instead of cookies or server sessions?
A: localStorage is simpler to implement for a school project. It persists
   across browser sessions and doesn't require server-side session management.
   The tradeoff: it's less secure than HTTP-only cookies because JavaScript
   can access it (vulnerable to XSS). For production, we'd use JWT tokens
   in HTTP-only cookies or a proper session server.

Q: What is BCrypt and why use it?
A: BCrypt is a password hashing algorithm. It converts a plain text password
   into a hash that cannot be reversed. It includes a built-in random salt so
   identical passwords produce different hashes. We use it because storing
   plain text passwords is a serious security vulnerability — if the database
   is breached, all accounts are immediately compromised.

Q: What is CORS and why do you need it?
A: CORS (Cross-Origin Resource Sharing) is a browser security mechanism that
   blocks JavaScript from calling APIs on a different domain/port than the
   current page. Our React app runs on port 3000, the backend on port 8000.
   Different ports = different origins = blocked by default. SecurityConfig.java
   whitelists localhost:3000 and 3001 so the browser allows these calls.

Q: What is JPA / Hibernate? What is an ORM?
A: ORM = Object-Relational Mapper. Hibernate is an ORM that maps Java objects
   (classes with fields) to database tables (rows and columns). Instead of
   writing "INSERT INTO users (email, password) VALUES (?, ?)", you write
   userRepository.save(userObject) and Hibernate generates the SQL for you.
   JPA (Java Persistence API) is the standard interface; Hibernate is the
   implementation.

Q: What is a DTO and why use them?
A: DTO = Data Transfer Object. A simplified, safe version of a database entity
   used for API responses. We use DTOs to: (1) avoid circular references that
   crash the JSON serializer, (2) exclude sensitive fields like passwords.
   For example, BookingDTO has userName and userEmail instead of embedding the
   full User object (which would include the password hash).

Q: What does ddl-auto=update mean? What are the other options?
A: It controls how Hibernate manages the database schema:
     create        — drops and recreates all tables on startup (loses data!)
     create-drop   — creates on startup, drops on shutdown
     update        — creates new tables/columns, never drops (our choice)
     validate      — checks schema matches entities, fails if not (production)
     none          — does nothing (you manage schema manually)
   We use "update" because it's safe for development — new Entity fields
   automatically get new columns.

Q: How does the app work when the backend is offline?
A: The data layer (appData.js, adminData.js) uses try/catch on every API call.
   On first successful load, property and booking data is cached in localStorage.
   If the backend goes down, the catch block returns the cached data instead.
   This "offline-first" pattern ensures the app doesn't show blank errors.

Q: How does role-based access control work?
A: When admin@vacansee.com logs in, Login.jsx detects the email and stores
   userRole="admin" in localStorage. App.jsx reads this to decide which routes
   to allow. The /admin route is only rendered if isAdmin=true; otherwise it
   redirects to /login. This is frontend-only role enforcement — the backend
   does not check roles on API calls (all endpoints are permitAll).

Q: What is the purpose of the @CrossOrigin annotation on controllers?
A: It's a secondary CORS configuration at the controller level. SecurityConfig
   handles CORS at the security filter level (first layer), and @CrossOrigin
   handles it at the MVC level (second layer). Having both ensures CORS headers
   are set regardless of which Spring layer processes the request.

Q: How are images stored for property listings?
A: When admin uploads a photo, the browser reads it as a base64 string using
   FileReader.readAsDataURL(). This string (starts with "data:image/jpeg;base64,")
   is sent to the backend and stored in the featured_image column which is
   LONGTEXT type to accommodate large strings. The same string is used directly
   as the src attribute of <img> tags in the frontend.

Q: What is the purpose of @JsonIgnoreProperties?
A: Prevents infinite recursion during JSON serialization. Booking entity has
   a Property field. Property would have a User (owner) field. If User had a
   List<Booking> field, Jackson would loop: Booking→Property→User→Bookings→
   Booking→... forever, causing a StackOverflowError. @JsonIgnoreProperties
   tells Jackson to stop at that field and not follow it further.

Q: Why do we manually delete related records before deleting a property?
A: MySQL enforces foreign key constraints. The bookings table has a
   property_id column that references properties.id. If you try to delete a
   property that has bookings, MySQL throws: "Cannot delete parent row: foreign
   key constraint fails." We must delete child records (bookings, inquiries,
   favorites, reviews, images) before deleting the parent (property).

Q: What happens when a new user registers?
A: Register.jsx validates the form, then calls authService.register() which
   POSTs to /api/auth/register. AuthController checks if the email is already
   in MySQL (existsByEmail). If not, BCryptPasswordEncoder.encode() hashes the
   password and a new User is saved to MySQL. The response includes the new
   user's database ID, which is stored in localStorage so future API calls
   (like addBooking) can reference the correct user ID.
